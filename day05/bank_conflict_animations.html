Transpose: read vs write
Broadcast
32 lanes of one warp · lane t reads s[t * 1] · bank = (t × stride) mod 32
The rule: with stride s, lane t lands on bank (t×s) mod 32. That map hits 32 / gcd(s,32) distinct banks, with gcd(s,32) lanes piled on each one — so the conflict degree is exactly gcd(stride, 32) and the warp pays that many transactions.

The consequence students usually miss: every odd stride is conflict-free. Stride 3, 7, 17, 31 all give gcd = 1 and cost one transaction, same as stride 1 — try them. Only strides sharing a factor of two with 32 hurt, and the damage doubles with each factor: 2→2-way, 4→4-way, 8→8-way, 16→16-way, 32→32-way. This is why padding a tile to [TILE][TILE+1] works — it turns an even row stride into an odd one.
A 32×32 __shared__ tile in a transpose kernel. The write is by row, the read is by column — same tile, wildly different cost.
layout:
words this warp touches rest of the tile
Write by row (tile[ty][tx] = in[...]): consecutive lanes touch consecutive words, stride 1 — always conflict-free, whatever the layout.
Read by column (out[...] = tile[tx][ty]): consecutive lanes step a whole row apart. With tile[32][32] the row stride is 32 words, so all 32 lanes hit bank 0 — a full 32-way conflict, the single worst case shared memory has. The kernel looks innocent; it runs ~32× slower on that access.

Two fixes, same result, different trade-off. Padding to [32][33] makes the row stride 33 words, so lane t lands on bank (33t + c) mod 32 = (t + c) mod 32 — all distinct. Cost: one wasted column of shared memory per row (128 bytes here), and it doesn't generalise to vectorised (float4) access. Swizzling with tile[r][c ^ r] puts lane t on bank c ^ t — also all distinct, with zero wasted memory, but you must apply the same XOR on both the write and the read, and the clean permutation only holds when the row width is a power of two.
All 32 lanes read the same address. Naively that looks like the worst possible 32-way conflict.
 
It isn't. Shared memory has a broadcast path: when multiple lanes in a warp request the same word, the bank reads it once and fans it out to all of them in a single transaction. A conflict only happens when lanes want different words that happen to live in the same bank.

So the real rule is narrower than "don't let two lanes share a bank": same bank + same address = free (broadcast); same bank + different addresses = serialized. This is why a lookup table every thread reads identically is fine in shared memory, and why constant memory (which broadcasts by design — see ARCHITECTURE.md) is a good home for that kind of data in the first place.
