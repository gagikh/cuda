The mapping: lane t reads word t × stride, which lives in bank (t × stride) mod 32. Every wire landing on the same bank is one more serialized transaction — the bank can only serve one word per cycle, so the whole warp waits for the busiest one.

The rule that falls out: that map covers 32 / gcd(s,32) distinct banks with gcd(s,32) lanes piled on each, so the conflict degree is exactly gcd(stride, 32).

The part most people get wrong: every odd stride is conflict-free. Drag to 3, 7, 17, 31 — the wires cross wildly but never collide, and the cost is one transaction, identical to stride 1. Only strides sharing a factor of two with 32 hurt, and each extra factor doubles the damage: 2→2-way, 4→4-way, 8→8-way, 16→16-way, 32→32-way. Padding a tile to [TILE][TILE+1] isn't magic — it just forces an even row stride to become odd.

Why there's no "stride 3-way" button: sweep the whole slider and you'll only ever see degrees 1, 2, 4, 8, 16 and 32. That's not a gap in the demo — gcd(s, 32) divides 32, so from a constant stride the conflict degree is always a power of two. A 3-way (or 5-, or 7-way) conflict is perfectly real, but it can only come from an irregular access pattern: an indirect gather s[idx[t]], a lookup table, a compaction, or any index the compiler can't express as t × k. Switch to gather above and dial in any degree you like. The practical upshot: if you're writing a regular tiled kernel, checking gcd(row_stride, 32) tells you everything; if you're writing a gather, the only way to know is to profile it (ncu --metrics l1tex__data_bank_conflicts_pipe_lsu_mem_shared).

Write by row (tile[ty][tx] = in[...]): consecutive lanes touch consecutive words — stride 1, conflict-free under every layout.
Read by column (out[...] = tile[tx][ty]): consecutive lanes step a whole row apart. With tile[32][32] the row stride is 32 words, so all 32 wires funnel into bank 0 — a full 32-way conflict, the worst case shared memory has. The kernel looks innocent; that one access runs ~32× slower.

Two fixes, same result, different trade-off. Padding to [32][33] makes the row stride 33 words, so lane t lands on bank (33t + c) mod 32 = (t + c) mod 32 — all distinct. Cost: one wasted column per row, and it doesn't survive vectorised (float4) access. Swizzling with tile[r][c ^ r] puts lane t on bank c ^ t — also all distinct, zero wasted memory, but you must apply the same XOR on both the write and the read, and the clean permutation only holds when the row width is a power of two.
All 32 lanes read the same address. Naively that looks like the worst possible 32-way conflict.
 
 
It isn't. Shared memory has a broadcast path: when several lanes request the same word, the bank reads it once and fans it out to all of them in a single transaction. A conflict only happens when lanes want different words that happen to share a bank.

So the real rule is narrower than "never let two lanes share a bank": same bank + same address = free (broadcast); same bank + different addresses = serialized. That's why a lookup table every thread reads identically is perfectly fine in shared memory — and why constant memory, which broadcasts by design (see ARCHITECTURE.md), is the natural home for that kind of data in the first place.
